# Handcrafted Frontend

Sites look AI-made for one reason: every decision was left at its default. The fonts, the palette, the section order, the card style, the fade-in, the copy. Any single default is fine. A stack of them is the fingerprint.

This skill replaces defaults with decisions. The rule for every choice: **you must be able to say why this choice fits this client, in one sentence.** If the only reason is "it looks modern" or "it's common", it is a default. Pick again.

Read these as needed, not all up front:

- `references/slop-tells.md` : the full catalogue of visual, copy, and code tells with fixes. Read before an audit.
- `references/type-and-colour.md` : how to pick fonts and build a palette, with over-used lists. Read before choosing type or colour.
- `references/code-standards.md` : how the code itself should look (HTML, CSS, Tailwind v4, React/Next). Read before writing components.
- `references/reference-workflow.md` : how to turn screenshots and reference sites into a design without cloning them. Read when the user supplies references.
- `references/immersive-effects.md` : when a 3D scene, shader gradient, glass panel, liquid logo or scroll-scrubbed video is allowed, the vetted libraries (React Three Fiber, ShaderGradient, Paper Shaders, liquid-logo, scroll-world, liquid-glass-js) with the bugs found in each, budgets, and supply-chain rules. Read before adding any of them.
- `templates/effects/` : tested Next.js components for those effects, each behind a poster, a reduced-motion gate and an error boundary.
- `templates/DESIGN.md` : the design brief template. Copy it into the project root.
- `scripts/slop-check.mjs` : a zero-dependency scanner for tells. Run it at the end of every build.

## Before anything: respect the project

1. Read the project's own `AGENTS.md`, `CLAUDE.md`, `GEMINI.md`, and `README.md` first. Project rules win over this skill on stack and conventions (for example, a Next.js version warning telling you to read local docs).
2. Detect the stack from `package.json` and the file tree: plain HTML/CSS, Next.js + Tailwind, Vite + React, etc. Work in the stack that is there. Do not add a UI kit, animation library, or icon pack that is not already installed unless the user agrees.
3. If a `DESIGN.md` exists in the project root, it is the source of truth. Follow it and update it when decisions change.

## Workflow

### Step 1. Write the brief (DESIGN.md) before any code

Copy `templates/DESIGN.md` to the project root and fill it in. Pull answers from the user's message, existing content, the business itself, and any files in the project. If something is missing and cannot be inferred, write a sensible choice marked `[ASSUMED]` and keep going rather than stalling. The user can correct it.

The brief must pin down:

- **The one job of the page.** What should a visitor do or believe after 10 seconds? Every section must serve this.
- **Audience and place.** Who, where, on what device and connection. A site for Lagos parents on mobile data is designed differently from one for London recruiters on laptops.
- **A concept.** One concrete image or metaphor the design grows from, taken from the client's world. "A night-study desk lamp", "a printed church bulletin", "a lab notebook", "a market receipt". Not "modern and clean". The concept is what makes the choices below non-random.
- **Type, colour, spacing, radius, motion** decisions, each with its one-line reason tied to the concept.
- **What this site will NOT do.** List the specific defaults you are rejecting.

Put a short version of the concept as a comment at the top of the main stylesheet or theme file, so the next developer (human or AI) sees the intent.

### Step 2. Build tokens first

Before any section, define the design system as tokens: colours, font families, a type scale, a spacing scale, radii, shadows (if any), durations, easing.

- Plain CSS: custom properties in `:root`.
- Tailwind v4: an `@theme` block. Remove the default palette with `--color-*: initial;` and define only the project's colours, so stock classes like `bg-indigo-500` cannot sneak in. See `references/code-standards.md`.
- Use the tokens everywhere. No raw hex values or magic numbers in components.

### Step 3. Structure from content, not from a template

Do not start from the standard AI landing page recipe: badge pill above a centred H1 with one gradient word, two buttons, logo strip, three icon cards, stats row, testimonial carousel, three-tier pricing, gradient CTA band, four-column footer.

Instead:

1. List the real content you have (or will have): offers, proof, people, prices, locations, FAQs.
2. Order it by what the visitor needs to decide, given the page's one job.
3. Give each section a layout that suits its content. A list of services might be a plain typographic list. A process might be a single paragraph. Proof might be one strong quote with a real name and photo, not six anonymous ones.
4. Vary rhythm between sections: change density, alignment, width, and background deliberately. Not every section gets a heading, a subheading, and a grid.

Asymmetry, big type, and unusual grids are tools, not goals. Over-correcting into "anti-slop" clichés (bento grids everywhere, noise textures, marquee tickers, cursor followers, giant italic serif words) is just the next default. Use them only when the concept calls for it.

### Step 4. Write real copy, or mark the gap

Copy is the biggest tell, bigger than colour. Follow the copy rules in `references/slop-tells.md`. In short:

- Specific beats impressive. Names, numbers, places, prices, dates, turnaround times.
- Banned words and patterns: elevate, seamless, unlock, empower, effortless, supercharge, leverage, cutting-edge, game-changing, next-level, "in today's fast-paced world", "whether you're X or Y", three-word triads ("Fast. Simple. Secure."), and em dashes as a crutch.
- Buttons say what happens next ("Book a 20-minute call", "Download the price list"), not "Get started".
- **Never invent proof.** No made-up testimonials, client logos, star ratings, user counts, or statistics. If real ones are not available, leave a clearly marked placeholder such as `[TODO: real testimonial from a named client]` and tell the user.

### Step 5. Build the components with restraint

Apply the defaults below unless DESIGN.md says otherwise with a reason.

- **Type:** a deliberate pairing from `references/type-and-colour.md`. Set a real scale. Use `text-wrap: balance` on headings and `text-wrap: pretty` on paragraphs. Keep body line length around 60 to 75 characters. Use tabular numbers for prices and stats.
- **Colour:** one dominant colour, one accent used sparingly, and neutrals tinted toward the dominant hue. No purple or blue-violet gradients. No gradient text. Body text passes WCAG AA (4.5:1).
- **Cards:** only for things that are genuinely separate objects (a product, an article, a person). Never nest cards. No coloured left or top border stripe. No lift-and-shadow hover on every card.
- **Icons:** one icon set, only where the icon adds meaning a word cannot. No emoji as UI. No icon on top of every feature card.
- **Effects:** no glassmorphism, glows, blurred colour blobs, or aurora backgrounds unless the concept demands it. Depth comes from type, contrast, and spacing.
- **Motion:** a few purposeful moments (page load, a state change, feedback on an action). Not a fade-up on every section. Always respect `prefers-reduced-motion`. See `references/code-standards.md`.
- **Signature effect (optional, at most one):** 3D, shader gradient, glass, liquid logo, or scroll-scrubbed video, only if DESIGN.md names it and it depicts something real about the client. Read `references/immersive-effects.md` first and build from `templates/effects/`. Never install a library or agent skill from a repo you have not read.
- **Images:** real photos of the real people, place, and product wherever possible. Set width, height, and meaningful alt text. No generic AI-rendered people, 3D clay figures, or abstract gradient blobs as filler. If no photo exists yet, use a neutral, clearly labelled placeholder box with the intended subject written in it.

### Step 6. Finish like a professional

The small things are where handmade sites show:

- A custom favicon and Open Graph image (not the framework's default logo). Remove boilerplate leftovers such as `next.svg` and `vercel.svg`.
- A unique `<title>` and meta description per page, one `<h1>` per page, a real 404 page.
- Designed focus states (visible, on-brand), a skip link, keyboard-usable menus and forms, a custom `::selection` colour.
- Forms with helpful, human error messages and a clear success state.
- Check at 360px, 768px, and 1440px widths. Nothing overflows or overlaps.

### Step 7. Audit, then fix

1. Run the scanner from the project root:
   `node <path-to-this-skill>/scripts/slop-check.mjs .`
   It reports tells by severity with file and line. Fix every HIGH item. For each WARN, either fix it or record in DESIGN.md why it is intentional.
2. If you can take screenshots (browser tools, Playwright), look at the page at mobile and desktop widths and compare it against DESIGN.md. Ask: "Could this page belong to a different business if I swapped the logo?" If yes, it is still generic. Go back to the concept.
3. Read the copy aloud in your head. Anything that sounds like an ad for nothing in particular gets rewritten or marked TODO.

Report to the user: what the concept is, the key decisions, what the scanner found and what you fixed, and every TODO placeholder they need to fill.

## When the user asks for 3D, shaders, glass, or scroll effects

Follow `references/immersive-effects.md`. In short: pick the technique from what is being shown (a product, a place, a logo), not from what looks impressive; one effect per site; poster first; gate for reduced motion, Save-Data and missing WebGL; lazy-load it; self-host every asset; check the bundle cost. If the request is "make it look premium" with nothing real to show, push back and say why.

## When the user gives you a reference (screenshot, URL, template)

Follow `references/reference-workflow.md`. The short version: extract the system (grid, spacing rhythm, type scale ratios, how sections transition), not the surface (their logo, photos, copy, exact colours, brand). Build the client's own design on that skeleton. Never reproduce another company's branded site, logo, or copy.

## Auditing an existing site

When asked to review or "de-slop" a site: run the scanner, read `references/slop-tells.md`, then report findings grouped by impact (copy and proof first, then type and colour, then layout, then code). Propose a concept and DESIGN.md if the site has none. Make changes only after the user agrees, unless they asked you to fix it directly.
